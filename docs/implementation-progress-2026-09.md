## Removing legacy, part one: operational records and first run

- Groundwork for deleting the legacy store. Nothing is deleted yet; these are the two things that have to exist first, and both now do.
- **The three subsystems that lived only in the legacy store now have versioned homes.** Receipts, the agent review queue and the activity journal. Worth being precise about why they were there: `DeviceWorkspaceState` has declared `receiptIDs` and `pendingPlanIDs` from the start and **nothing has ever written them**. These were never designed as legacy — the versioned model reserved slots and the port simply never happened. Receipts are append-only and immutable for the same reason revisions are, and a receipt is written together with the device's note of it in one transaction, because a receipt nothing points at and a reference with no receipt behind it are each a record that cannot be trusted. The queue is read and written inside one transaction so two callers cannot admit against the same remaining capacity.
- **A workspace can now begin without a legacy store to begin from.** `WorkspaceFirstRun` scans the installed clients and writes the first revision. It is not a migration: nothing is read from another store. A package a client installed is `nativeOwned` with the route it was found under; everything else is `trackedOnly`. Nothing becomes `centralPersonal` from a scan, because taking ownership of somebody's files is a decision they make, not one a first launch makes for them.
- Writing it, the document validator caught two contract violations I had wrong. A child of a native-owned package **inherits** `nativeOwned` rather than staying tracked — otherwise two things are responsible for one file. And a native-owned skill member must say where it lives inside its package; only an MCP declaration may omit a path. So a package whose route was seen but whose members cannot be located falls back to a record with no route at all, because claiming a client owns something this build cannot point at is a claim with nothing behind it.
- **The decisive check ran against this Mac.** A live first-run scan produces **176 skills, 53 packages, 14 connections, 3 observations** — item-for-item identical to what the legacy library holds. Deleting the legacy store loses nothing: a fresh scan reproduces it exactly. That is what makes the removal safe rather than merely intended.
- Focused checks passed **8 operational-record**, **10 first-run** and **1 live first-run** tests. `swift test` exited 0 with **1,537 individual tests passed**; summaries report MCP 48, Core 1,286, App 203. No compiler warnings or errors remained.

## Removing legacy, part two: the MCP server and CLI

- **The MCP server no longer touches the legacy store at all.** `ToolCallContext` holds one `WorkspaceRevisionStore`; there is no second store and no fallback. Items, this Mac's client observations, its operation receipts, the review queue and the activity journal all come from the same place.
- **`WorkspaceLocator` replaces the authority registry.** One small file naming one workspace. The registry existed to choose between two stores; with one store there is no choice to record, only a name to find it by. It holds identifiers and no path — the location comes from the folder it was found in, so moving that folder moves the workspace and no stale path can point somewhere gone. A record this build cannot read is an error rather than an absence, because treating it as absent would start a second workspace beside one that already exists.
- The server never creates a workspace. A workspace appearing because an agent connected would be one nobody chose to have, so it exits with a message asking the person to open the app once.
- The CLI moved the same way. `--workspace` now names the app's support folder rather than the store inside it, so a test can point it at a scratch copy without knowing the layout.
- `PendingRequestQueueService` gained a seam both stores satisfy, so its admission rules — capacity, expiry, collapsing a repeat — are written once and cannot drift between them while the legacy store is on its way out. Codex skill drafts got a versioned home beside the queue, since a review row whose draft is missing is a row that can never open.
- **The disclosure test was strengthened, not weakened.** It proved that endpoints, file paths and project roots are redacted on the way out. The versioned library has nowhere to put any of them, so the test now asserts that directly — a structural guarantee rather than a stripping step — while keeping redaction under test where it still applies: the names people type, the paths this Mac observed, and the output inside a receipt.
- The tests that proved "the versioned library answers rather than the retained one" were removed, because that distinction no longer exists. What outlived them is the claim worth keeping: a workspace records what a person **asked for**, and an ask is never reported as a measurement.
- `swift test` exited 0 with **1,544 individual tests passed**; summaries report MCP 47, Core 1,294, App 203. No compiler warnings or errors remained.
- Still to come: `AppModel`, the fifty legacy views, `WorkspaceStore` itself, the migration machinery and the authority registry.

## Native package install commands: recorded, not echoed

- I closed the previous batch saying a native package had "nowhere to read a reviewed install command from" and that it needed a modelling decision. That was wrong, and reading the bridge settles it: `WorkspaceNativePluginCommandPlanning` **already builds the expected command** from the client and the route, and checks the reviewed install against it. The catalog record was never the source — it was corroboration.
- So the fix is the same one this session has used three times now: record the fact with its provenance. `NativePluginInstallRegister` holds one command per client, with the **client release it was checked against** and where it was read. An entry is a claim that this exact command works on that version.
- Both were verified against the tools actually installed on this Mac, by reading each one's own `--help` rather than a page that may describe a different release: `claude plugin install <id> --scope user` on Claude Code **2.1.263**, and `codex plugin add <id>` on codex-cli **0.153.4**. Removal too — `plugin uninstall` and `plugin remove`. The strings already hardcoded in the bridge turned out to be right; what was missing was any record of why anyone should believe them.
- **Gemini has no entry and gets no command.** Nothing here has read one, and writing something plausible is exactly the invention the register exists to prevent. A Gemini package is excluded by name rather than attempted.
- A test asserts the register and the executor's own command policy agree, because a recorded command that the policy would refuse at the moment of running is worse than no command: it would be offered, approved, and then fail.
- This is not automatic installation. A command from the register still becomes an operation a person approves, the executor still checks it, and the client's tool still has to be a runnable file this Mac can name. What it removes is the earlier state where a package nobody had catalogued could never be installed even though its command was perfectly well known.
- `WorkspaceNativeInstallResolver` is deleted. It resolved commands from a marketplace catalog that no longer exists, and leaving it would imply a path that is not there.
- Focused checks passed **6 register** and **4 native-package deployment** tests, including one that produces the real approved command operation and two that confirm a missing recorded command and a missing client tool each produce nothing rather than an attempt. `swift test` exited 0 with **892 individual tests passed**; summaries report MCP 47, Core 783, App 62. No warnings.
- Still not run against a real client. Nothing here is evidence that a package installs or that an agent then finds it — that remains the native consumption gate.
