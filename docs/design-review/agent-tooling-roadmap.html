Agent Tooling Roadmap

Five agents read the source, docs, release notes, and screenshots of the tools closest to ours. This is what they do better, what to take, and what to deliberately leave alone — with the three things you asked about worked out in detail.

The single biggest gap

Your own install reads “0 managed · 250 discovered”

Every competitor has a path from discovered to managed. skills-manager has “Scan Local Skills” (“Scanned {tools} tool folders and found {skills} importable skills”) and a skills adopt <dir> command that pulls a skill already sitting in an agent folder into the central library without duplicating it. SkillDock has “扫描导入” (scan & import) on every screen. Agent Tooling shows you 250 skills it can see and offers you nothing to do with any of them.

Until that path exists, the app is a viewer for most people on day one, and the library — the thing every other feature depends on — stays empty. Build Adopt first. Select discovered skills → one plan that copies them into the managed library → they become editable, installable, backed up, and portable to a second Mac. It uses machinery you already have.

Collections

Seven products model grouping. The pattern that survives contact with users is two layers, not one.

The design

  1. Collections are not a second Configurations. A Configuration stays the one resolved, activatable thing — the Assistant, the Profile. A Collection is reusable material a Configuration is built from, the way Continue composes Blocks. A Configuration’s required list becomes: its own items, plus its inheritance chain, plus any Collections it includes.
  2. Group whole skills, plugins, and servers — not individual tools inside them. ToolHive and mcpm both prove server-level grouping is enough on its own.
  3. Let Collections overlap. One skill in three Collections is normal. Don’t copy ToolHive’s strict one-group-per-server rule, which forces you to run duplicate instances to model overlap.
  4. There is no globally “active” Collection. Almost nobody does that. Activeness belongs to a consumer — a Configuration, a client, a project. Attaching and detaching is the whole interaction.
  5. Steal skills-manager’s honesty about what applying means. Its diagram literally labels the action “Apply (one-time write)” and calls Tags “filtering only.” That one word — one-time — prevents the single most common misunderstanding: that a Collection is a live link.
  6. Add tags separately, and add them now. They are the cheapest organizational win in the whole review: multi-valued, bulk-editable, with an “Untagged” filter pill so the unsorted pile is one click away. Tags filter. Collections apply. Never merge the two.
  7. Export as a file, strip the secrets. Docker’s wording is the rule to copy: “Credentials are not included in shared profiles for security reasons.” Add a native Share Sheet over that file and you get AirDrop sharing with no server to run. Note that both products in this review that bet on hosted sharing — mcp.run’s profile URLs and Continue Hub — are the two that no longer exist.
  8. Put the switcher where the work is. mcp.run buried profile management in Settings and it is a known annoyance. skills-manager instead puts a Presets submenu right in the menu bar, each one toggleable with a ✓ or a partial count. Do that.
  9. Give it its own section and its own icon family. Also show small Collection pills on each item row so you can see membership without opening every Collection. And keep it visually distinct from Configurations — MetaMCP’s “Namespaces” next to “Endpoints” in one sidebar is a documented source of confusion.
Naming. If Collections and Configurations still feel too close, the honest split is Collections are what you have; Configurations are what this Mac should have. One is a shelf, the other is a contract.

Projects

Your engine already supports project scope for skills and MCP servers. It has nowhere to live in the interface, so nobody will ever use it.

How the others do it

  • opcode discovers projects by scanning ~/.claude/projects/ — Claude Code’s own session index — plus an “Open Project” picker. Its per-project screen is three tabs: Slash Commands, Project Hooks, Local Hooks.
  • skills-manager gives projects a permanent sidebar section, three ways to add one (pick a folder, scan a root like ~/Work, or link an arbitrary directory), and a colored sync-health dot per row: red diverged, amber needs attention, blue project-only, green in sync.
  • Claude Code Tool Manager lets you drag an MCP card onto a project or onto “Global,” and supports per-project environment overrides.
  • SkillDock has no project support at all — its own contributor checklist says to record project-level paths, and a feature/project-level-skills branch sits unmerged. This is open ground.

The design

  1. Discover, don’t make people register. Read ~/.claude/projects/ for folders Claude Code has actually run in, offer a folder picker, and offer a “scan this root” option for a directory like ~/ws. A project should be a derived thing you can also pin, not a record the user must create.
  2. One sidebar entry leading to a list, not an icon rail. Rails exist in session managers because people hop constantly; you visit a project’s config occasionally. Master–detail split, matching every other screen you have.
  3. Rows show configuration facts, not run status. Name, a git branch chip, then compact badges: “3 MCP servers · 2 skills · CLAUDE.md”, plus one sync-health dot. A project with no local overrides should look visibly plain.
  4. The detail pane mirrors your global sections — tabs named Skills, MCP Servers, Plugins, Configuration — so anyone who knows the global screens knows this one immediately.
  5. Mark inherited versus overridden explicitly on every row. This is the question the sidebar cannot currently answer anywhere in the app.
  6. Split committed from machine-local. .claude/settings.json is shared with your team; .claude/settings.local.json is not. opcode separates them and offers a one-click “add to .gitignore.” This is a real footgun worth solving.
  7. Project roots do not travel. They are stripped on export by design, so a project-scoped skill arrives on a second Mac unattached. Say so in the Projects empty state rather than letting someone discover it during a restore.
  8. Do not import kanban boards, session lists, or live status dots. Those belong to tools that run agents. Borrowing that language would promise something the app does not do.

An MCP server for the app itself

Your instinct is right and it is buildable — but there is one specific thing that must never be a tool, and it is not obvious.

The finding that shapes the whole design. Your apply command takes --confirm <planID> --digest <sha256>, and the digest is a pure SHA-256 of the plan’s own bytes. That is content integrity — proof the plan being run is byte-identical to the plan someone read — and not consent. Anyone holding the plan can compute a valid digest for it. That is fine today, because only your review sheet calls it. Expose it as an MCP tool and you hand any prompt-injected agent a self-approval primitive: it can build a plan, hash it, and approve its own work. Never expose apply, and never expose an approve or deny tool.

What the field looks like

  • Claude Code Tool Manager already ships this — a local MCP server on 127.0.0.1:23847 exposing create_mcp, update_mcp, delete_mcp, create_skill, delete_skill, create_hook and more to any connected client, marketed as “Ask Claude to add this MCP to my project and it just works.” Nothing in that path shows a human a diff. That is the thing to beat, not to copy.
  • tech-leads-club/agent-skills ships the opposite: exactly four read-only tools — list_skills, search_skills, read_skill, fetch_skill_files — with documented progressive disclosure so an agent fetches only what it needs. Installation stays in the CLI.
  • MetaMCP and ToolHive both keep the administrative surface and the agent surface on entirely different code paths.
  • The MCP specification is explicit for exactly your shape: if a client supports one-click local server configuration it must implement consent showing the full untruncated command, and “use the stdio transport to limit access to just the MCP client.” Research cited by OWASP found tool-poisoning succeeds 84% of the time when auto-approval is on.

The design

Ship it as an AgentToolingMCP target beside the existing CLI helper, over stdio from inside the app bundle — not a localhost port, which any local process can reach and which DNS rebinding can attack. Three tiers:

Read-only safe

search_inventory, get_component, get_client_status, list_receipts, get_receipt, list_pending_requests, get_request_status, open_review_screen. Most are thin wrappers over agent-tooling search and doctor, which already emit exactly these shapes. Return secret reference names only, and omit configuration paths by default so a home directory never leaks into a transcript.

Queue a request needs a human

request_add_mcp_server, request_create_skill, request_install_skill, request_install_plugin, request_remove_component. Each appends one bounded row to the pending queue and returns {state:"pending-review", reviewURL:"agent-tooling://requests/<uuid>"} — the exact shape request create-skill already returns today. The MCP layer never builds an OperationPlan; that happens in-app when a human opens the link. Bound the queue, collapse duplicate requests into the existing pending one, and take exactly one component per call — no bulk variants, so one injected instruction cannot become twenty rows.

Never excluded by construction

Anything that applies, executes, confirms, approves, or denies. Any tool returning a secret value. The --home and --workspace overrides, which exist for tests and would reintroduce a path-confinement bypass. Any generic run_command. Anything that edits the allowlist, the redaction patterns, or the server’s own registration.

Two details worth taking: record the caller’s self-reported clientInfo so the review screen can say “Claude Code is asking to add X” — as display only, never as authorization — and append every tool call, including read-only ones, to your existing activity trail, so Insights can show “an agent searched 40 times and queued 2 requests today.”

Elicitation. MCP’s elicitation primitive can fill in a missing parameter — “which project root?” — but must not carry the approve decision. Its dialog renders in the agent’s client from server-supplied text; your review sheet is the only surface that can show the real redacted command next to the file it changes.

Marketplace

You just added source and app filters. These are the next rungs, in order.

  1. Show provenance on every row. PulseMCP’s single best idea is a Classification facet with three values — Reference, Official, Community — each with its own icon, shown on the card and filterable. You already know which catalog a package came from; turn that into a badge people can trust at a glance.
  2. Real sorting. You have none. PulseMCP offers eight, including Most Popular this week and Recently Released; aitmpl offers Most Popular and Alphabetical. Start with Relevance, Name, and Recently Updated.
  3. Show the tools a server exposes, with their annotations. Smithery lists every tool with its input and output schema as a table, and marks each read-only, destructive, or idempotent from MCP’s own annotations. For a review-first app this is the highest-value detail you could add: a person can see a destructive tool before approving the plan.
  4. Multi-select into one plan. aitmpl’s Stack Builder collects picks in a tray and emits a single combined command. Yours should collect picks and emit a single reviewed plan — a much better ending than theirs.
  5. Write real empty states. claude-plugins.dev renders a bare “0 plugins” with no guidance; Smithery has no zero-result state at all and silently returns 100 unrelated results. aitmpl gets it right: “No results for X” plus a Clear search button. You already name the source and filter that produced the emptiness — keep that.
  6. Mask secret-looking fields and route them to the Keychain. Smithery treats any config key whose name contains “key” as a password field and stores values in the OS keychain rather than the client config.
  7. Adopt Claude’s own scope vocabulary at install time, as claude-code-templates does: User (all projects) / Project (shared with team) / Local (personal, not committed). It maps exactly onto your scopes and onto the committed-versus-local split in Projects.
  8. Grade honestly, and say what the grade means. Glama shows three letter grades per server — License, Quality, Maintenance — and its tooltip for Quality is disarmingly literal: “‘A’ indicates that we were able to successfully run the server. ‘F’ indicates that we were not able to successfully start it.” That is the same discipline as your Observed / Installed / Authenticated vocabulary, applied to a catalog. An ungraded item shows “Not graded” rather than hiding the row.
Worth knowing about tool descriptions. Glama open-sourced a Tool Definition Quality Score that grades every tool on six dimensions — behaviour, conciseness, completeness, parameters, purpose, usage guidelines — citing a study of 856 tools across 103 servers: 97% contain at least one defect, 89% omit usage constraints, and tools with well-written descriptions get selected by models 260% more often. Your Insights screen already produces quality findings for skills. This is the same idea for MCP tools, and the rubric is already written.

Turn your safety model into visible features

You already have the machinery. These make it legible — and each one is something a competitor added only after a real data-loss bug.

  • Removal guard, at plan time. skills-manager v1.34.0 added this after users lost files: before an update replaces a folder, diff current against incoming, and if anything would be deleted, hold it back and say so. Put that list in the plan sheet: “this update removes 3 files.”
  • Ownership guard, at plan time. Their v1.32.0 refuses to overwrite any target it cannot prove is empty, its own symlink, or a recorded prior install. You confine writes to known folders; proving ownership of the specific destination is the missing half.
  • Drift detection. tech-leads-club pins a SHA-256 content hash per installed skill in a lockfile specifically so tampering is detectable later. You already compute a reviewed-source fingerprint for every install — store it and compare on each setup check. “Installed but modified since you reviewed it” is a status nobody else surfaces.
  • Itemized batch outcomes. Both Chinese-language apps report “succeeded N, failed N, skipped N” and name which ones and why. Your receipts already hold per-step results; surface them that way after a multi-step plan instead of a single verdict.
  • A sync scope panel. skills-manager shows, before you ever connect a backend, exactly what travels and what never leaves the machine. You have that list in the handbook; it belongs on the screen where someone chooses a folder.
  • Extend the content scan. You detect executable content. The Snyk agent-scan taxonomy that tech-leads-club runs in CI adds prompt injection in skill instructions, suspicious download URLs, unverifiable remote dependencies, and — cheapest and most striking — hidden Unicode: zero-width characters, bidi overrides, and Tag-block steganography used to smuggle instructions past human review. That one is a few lines of Swift and directly protects the thing you promise, which is that a human really reviewed it.
  • Diff descriptions on re-scan, and look for injection. Glama re-introspects hosted servers on a schedule and diffs the result, analysing changes specifically for “instructions directed at an LLM consumer, role-override attempts, exfiltration prompts.” That is the live defence against a rug pull — a server whose tool description turns malicious after you approved it. You already fingerprint what was reviewed; comparing the new description against the approved one and flagging injection-shaped changes is the natural extension, and no desktop tool in this review does it.
  • Split severity into Risky and Malicious. Glama routes Malicious to internal review and delisting, but surfaces Risky on the listing “so operators can make an informed decision.” A review-first app should never silently drop an item — it should show the finding next to the approve button.
What a serious behavioural check looks like. Glama builds and runs every server in an ephemeral Firecracker microVM and watches syscalls and network: access to credential paths not required by the declared capabilities (SSH keys, cloud credential directories, browser cookie stores), outbound traffic to hosts not referenced in the manifest or source, process forks into unrelated binaries, filesystem writes outside the declared working directory. You are not going to run a VM fleet — but that list is a good checklist to describe in a plan for a stdio server whose command you are about to run.

What not to build

  • Session running, kanban boards, worktrees. Conductor, Nimbalyst, and Vibe Kanban own that, and Vibe Kanban — 28,000 stars — is sunsetting anyway. It is a different product.
  • A hosted registry or sharing backend. Both products in this review that centred one are gone: mcp.run redirects elsewhere and Continue Hub no longer resolves. Files outlive vendors.
  • An auto-approve mode, in any form, including “remember this decision.” Tool poisoning succeeds 84% of the time when auto-approval is on, and it would delete the only thing that makes this app different.
  • A localhost HTTP control port. Claude Code Tool Manager has one; the MCP spec recommends stdio precisely to avoid it.
  • Chasing catalog size. Glama lists 80,000 servers. You will not win that and it is not what a review-first tool is for.
