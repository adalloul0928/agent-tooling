The mental model

Three things, left to right. Learn this and the whole app reads at a glance.

Library is everything Agent Tooling knows about: packages it manages for you, plus everything it found already installed on this Mac. Configuration is the desired state you name and switch between. Clients are the three command-line apps that actually run your tooling.

The app never writes to a client as a side effect. Every action that would change a client first produces a plan you read and approve, and every executed plan leaves a receipt.

The row grammar

Almost every list uses the same four parts: a colored tile for what kind of thing it is, its name, one clause of detail, and a verdict on the right. Colors are stable across the whole app.

Skill
Plugin
MCP server
Configuration

A tile at half strength means the item was discovered on this Mac but is not managed by Agent Tooling. Small brand marks show which clients carry it; a dimmed mark means that client does not have it. File paths never appear in a list — they live behind the ⓘ button in the detail pane.

Managed vs. discovered

This distinction runs through everything. A managed item was created or imported through Agent Tooling, so its canonical source lives in the app's library and it can be installed, edited, backed up, and carried to another Mac. A discovered item was found in a client's own folders. It is shown, searched, and counted, but the app does not own it: it will not edit it, sync it, or include it in a backup.

Setup

Build the bundle once, then open it like any other Mac app.

Requirements

  • macOS 26 or newer, with Xcode 27 and Swift 6.2 to build it
  • At least one of Claude Code, Codex, or Gemini CLI installed — the app is useful with one, and none is a valid state
  • No GitHub account, no remote, no sign-in of any kind
cd apps/agent-tooling-macos
./scripts/package-app.sh
open '.build/Agent Tooling.app'

Pass a destination to install it properly, then it behaves like a normal application including Open at login:

./scripts/package-app.sh '/Applications/Agent Tooling.app'

What the first launch does

It creates ~/Library/Application Support/Agent Tooling containing a SQLite database, the managed package library/, a cache/, and later an exports/ folder for backups. Then it runs one read-only scan and opens on Overview.

The scan reads configuration files and asks each installed CLI for its inventory. It writes nothing. These are the exact places it looks:

Worth setting on day one

  • Settings → General: keep Check health automatically on so each launch refreshes reality; decide whether you want the menu bar item and Open at login.
  • Configurations: the app starts with one called Local Library. Rename it or add a second one before you start ticking required plugins and servers.
  • Settings → Library & Sync: if you already know you want a second Mac, set up encrypted folder sync now and store the recovery key — see Multiple computers.
Nothing is installed by setup. A fresh install shows everything you already had, with zero managed items. The library fills up only when you create or import something.

What it does not touch

Only those three CLIs have adapters. The following are deliberately outside the app's reach, and it will not pretend otherwise:

  • Claude Desktop — not scanned, not configured. Its MCP configuration is separate from Claude Code's, and Agent Tooling has no adapter for it. You can record a connection note against it, nothing more.
  • ChatGPT desktop and ChatGPT web — same. Local Codex configuration is not inherited by ChatGPT, which is exactly why the Accounts screen calls that out.
  • Claude.ai, Gemini web, IDE extensions — account-level surfaces. They are listed so you can record when you last checked them.
Why the line is drawn there. The three CLIs expose documented, scriptable configuration on local disk. The desktop and web surfaces do not, so anything the app claimed about them would be a guess. It records your own verification instead of inventing a status.

What it manages, in its own library

  • Skills — portable packages it can create with Codex, import from a folder or repository, install, edit, validate, back up, and carry to another Mac.
  • MCP servers — definitions you write once and then configure per client with native commands.
  • Plugins — observed everywhere; installed through each client's own plugin manager, never by copying files.
  • Configurations — named desired state with inheritance.
  • Catalog sources — Agent Plugins folders and Git checkouts you add, plus the official MCP Registry and each client's native catalog.
  • Connections — metadata about who owns an authorization and where you verified it.

Check vs. Review

Two actions, four labels. One looks, the other proposes.

Check Now · Check Clients · Check Setup ⇧⌘D

Reads only Rescans all three clients, refreshes the skill, plugin, and MCP inventories from what is actually on disk, and writes a Setup check completed receipt listing the configuration files it inspected. It never changes a client. Run it after installing a CLI, after editing something outside the app, or whenever a screen looks stale.

Review Sync · Review Changes · Sync Agent Tooling ⇧⌘R

Proposes a change Compares your managed skills against the clients each one targets and builds a plan: one copy step per skill per client, plus a verification rescan. Nothing happens until you press Run N steps. If there is nothing to sync it says so rather than inventing work.

Both appear on Overview with short labels and on the Sync screen with longer ones; the menu bar item carries both too. The number on the Review Sync button is the attention count, not a queue: MCP servers needing setup, plus failing checks in the current configuration, plus clients whose command was not found.

Sync covers managed skills only. It does not push MCP servers or plugins. MCP servers are configured per client from their own detail pane, and plugins install through Marketplace, because both go through native commands rather than file copies.

Create a skill with Codex

New skill uses the Codex CLI you are already signed in to. Claude is never invoked as a generator, and no API key is requested or stored.

  1. Open Skills and press ⌘N, or click New skill…
  2. Describe the workflow in plain language: what it should do, when it should be used, and any constraint it must follow. A suggested name is offered and you can replace it.
  3. Choose the install scope, This Mac or a project folder, and tick which clients should receive it later.
  4. Click Generate draft. Codex runs in an isolated staging folder with your own configuration, plugins, and hooks disabled.
  5. Read every generated file. The Save button stays disabled until each one has been opened.
  6. Click Save skill and review install. The package is written into the managed library and an install plan opens.
  7. Approve the plan, or cancel and install later from the skill's detail pane.

Managed skills carry a Managed by Agent Tooling label, a definition-check count, and a Reveal Source in Finder action. Skills you wrote by hand also get an Edit… button that reopens the five-step editor: purpose, triggers, placement, bundled files, review. Codex-generated packages deliberately omit that editor so their richer source is never flattened by a template.

Add an MCP server

Two steps: the connection, then which clients get it.

  1. Open MCP Servers and click Add server…
  2. Name it in lowercase words separated by hyphens; the sheet rejects anything that would not make a valid identifier and says so immediately.
  3. Pick the transport, HTTP or stdio, then give the endpoint URL or the launch command.
  4. Choose authentication and scope, then continue and switch on the clients you want.
  5. Click Add server. Desired state is saved and a plan opens showing the exact native command for each client.
  6. Approve to run them, or cancel to keep the definition and configure a client later from the detail pane's Set up… menu.

Each client is configured independently, so one failure never rolls back another client's success. The Remove… menu builds the matching removal command per client. Authentication is always a guided manual step: the app records that a server needs it and points you at the owning product; it never copies a token between clients.

Configured is not authenticated. A green verdict means the server is present in that client's configuration. Live tool health and OAuth are separate checks that belong to the server and the client.

Why no skills appear in the built-in catalogs. None of them publishes standalone skills: Claude and Codex catalogs list plugins, and the registry lists MCP servers. A plugin may contain skills, but the catalog entry is still a plugin. Skills show up when you add a source that actually contains them — an Agent Plugins folder or a checked-out repository with skills/ directories. Each source row shows its own breakdown, so you can see at a glance which one carries what.

Narrowing the list

Click a source to show only its packages; click it again, or the × on the filter chip, to go back to everything. The two menus below the search field narrow by component — skills, plugins, MCP — and by app, so Claude Code hides anything that has no Claude install route. When a combination has no results, the empty state says which source and filter produced that, rather than looking like a failed fetch.

Adding your own catalog

  1. Clone the repository yourself, wherever you keep checkouts.
  2. Add source… and pick that folder. It is inspected immediately and its packages join the list.
  3. Refresh whenever you want to re-read it.

There is no background fetch. A Git-backed source is read from the working copy on disk, so to pick up upstream changes you git pull it yourself and press Refresh. That is a deliberate boundary: the app's entire Git vocabulary is init and status inside its own backup folder, so it never runs a network Git operation on your behalf or executes code from a remote you have not looked at. If you want it automatic, a git pull on a schedule — a cron entry or a launch agent — plus Refresh gives you the same result with the fetching under your control.

Project-level scope

Skills, MCP servers, and configurations can all be scoped to one project folder instead of the whole Mac.

Choose Project in the skill editor's Placement step, in the MCP sheet's Scope row, or when creating a configuration, then pick the folder. The folder must be a real directory, not a symlink, and the app re-verifies it at approval time.

For project and local scope the command runs with the project folder as its working directory, and the engine accepts that directory only when it exactly matches the project root you reviewed.

Codex has no MCP scope flag. Rather than quietly writing a project server into your global Codex config, the plan turns that step into a manual review that names the situation. Claude Code and Gemini CLI take the scope natively.

Project scope and multiple Macs

Project roots are absolute paths, so they are stripped from anything that leaves this Mac. A project-scoped skill arrives on the second Mac as a managed package with no folder attached; pick the local folder there and install it again. This is deliberate — the same repository rarely sits at the same path on two machines.

Configurations

A configuration is a named list of what this Mac, or one project, should have. Switching one never writes to a client by itself.

Create one from New configuration… with a name, a summary, a scope, and optionally a parent to inherit from. Then use Edit configuration… to tick the plugins and MCP servers it requires.

Inheritance merges: a child gets everything its parent requires plus its own additions. Make Current switches which one Overview compares against, and its health checks report how many requirements are satisfied right now. To close the gap, configure the servers and install the plugins; the configuration is the checklist, not the installer.

Names must be unique. A duplicate is refused with a plain explanation rather than silently creating a second entry with the same identifier.

Sync and receipts

Sync is a comparison first and a change second.

The Sync screen opens with an installation map: one row per kind of tool, one column for the library and one for each client, so you can see at a glance that Claude has fewer skills than Codex or that Gemini has no MCP servers. Below it, each client reports whether its command-line tool was found.

Approving a plan runs its steps and records a receipt, then a fresh scan runs so the screens reflect reality rather than intent. Every receipt in Activity keeps the operation type, start time, duration, an identifier, the affected local paths behind ⓘ buttons, and the executed command behind a disclosure with a Copy action. Receipts are redacted before they are stored.

Insights

Scan recent local chat history to find repeated work, unused skills, and gaps worth filling.

Choose the sources, Claude Code and Codex, a review period of seven, thirty, or ninety days, and how many conversations per source to inspect. Optionally allow catalog suggestions, which sends broad capability topics from an audited list to connected catalogs; your chat text and local names never leave the Mac.

The report has three parts: coverage, telling you honestly how much it read and what it skipped; opportunities, each of which can open the matching skill or marketplace package; and quality findings on the skills you already have.

What is stored. Chat text is processed transiently. The report keeps aggregate counts and recommendations, never messages or excerpts.

Multiple computers

There is no cloud account, so identical setups come from a file you control. Pick encrypted folder sync for personal machines, a Git backup if you want history, and a policy manifest for other people.

Encrypted folder sync — the normal answer

One AES-GCM encrypted file, agent-tooling.encrypted.json, written into any folder you choose, including one that iCloud Drive, Dropbox, or a NAS happens to sync. The key never travels with it.

  1. Mac 1: Settings → Library & Sync → Encrypted archive → Choose folder…, then approve the export plan.
  2. Mac 1: click Copy key and put the Base64 recovery key in your password manager. Without it the archive is unreadable anywhere else.
  3. Mac 2: install the app, then Settings → Library & Sync → Import key… and paste that key before touching the archive.
  4. Mac 2: Import encrypted archive → Inspect…, point at the file, read the preview, then run the restore plan it produces.
  5. Mac 2: press ⇧⌘R and approve, which installs the managed skills into the clients there.
  6. Mac 2: open each MCP server and use Set up… per client, and reinstall any plugins from Marketplace. Those are native commands, so they do not ride along in a file.

Repeat the export whenever the library changes. It is a snapshot, not a live channel: two Macs never negotiate, the newest archive simply wins at the moment you choose to restore it.

What travels

  • Managed skills and their actual package files, with POSIX permissions preserved
  • MCP server definitions you created — observed ones from a client's own config are dropped
  • Configurations, including inheritance
  • Imported managed policies
  • Catalog sources that are http or https
  • Connection records and account surfaces, with every verification reset to unverified

What does not travel

  • The encryption key — Keychain only, moved by you
  • Plugins, and the cached marketplace listings
  • Anything merely discovered on the first Mac: observed skills, observed servers, scan results
  • Activity and receipts, which are a log of one machine
  • Project roots, local folder sources, the imported repository path, and backup or sync settings
  • Client installation state — the second Mac decides that for itself, which is why you sync after restoring

Local Git backup — when you want history

Prepare Backup… exports the same portable state plus the package library into exports/git-backup inside the workspace and runs git init there. The app's entire Git vocabulary is init and status: it never commits, adds a remote, or pushes, and the plan includes a manual step reminding you that connecting a remote is your decision. Commit and push it yourself, clone it on the second Mac, then use Inspect… to review and accept it. A backup that already exists and has uncommitted changes blocks the export rather than overwriting your work.

Managed policy — for a team or a fleet

Ship a data-only agent-tooling-policy/v1 JSON file through a shared folder or a checkout. Each person imports it from Settings → Policy & Safety, and it can add managed configurations and block named plugin identifiers. It carries no scripts and is never fetched in the background, so it standardizes intent without becoming remote control.

Choosing between them. Encrypted sync moves the packages themselves and is the one to use for your own second Mac. Git gives you diffs and history for a library you evolve deliberately. A policy shares the shape of a setup with people whose libraries you do not own.

Connectors and accounts

Cloud connectors belong to the product that issued them. Agent Tooling tracks them as facts about your setup, never as things it can change.

The Accounts screen seeds three cloud surfaces and links straight to where each one actually lives:

SurfaceWhy it is separate
Claude.ai connectorsAccount connectors are not Claude Code configuration. Verify them in Claude's account settings.
ChatGPT apps and connectorsChatGPT web does not inherit local Codex configuration. Verify hosted apps in ChatGPT settings.
Gemini account and enterprise extensionsGemini web and managed workspace resources need account or administrator verification.

Each row has Open settings, which opens the real page, and Record verification, which stamps the date you checked. That timestamp is the whole feature: an honest note that you looked, rather than a status the app cannot actually observe.

Recorded connections

Record connection… captures a name, provider, who owns the authorization — local client, product account, external secret manager, or organization admin — the surface it should appear on, a scope, and optionally the names of the secrets involved, such as LINEAR_API_KEY. The sheet says it plainly: no login, token, or secret value is collected. Each connection gets a binding you can mark verified, and removing one deletes only Agent Tooling's note; it never revokes anything upstream.

So what about a Claude Desktop or ChatGPT connector? Set it up in that product, then record it here so your inventory is complete and you know when you last checked it. The app has no adapter that could configure it, and it will not claim one.

What keeps it safe

Five rules hold everywhere, including from the command line.

Review before change

Nothing touches a client until a plan is approved. The plan lists each step, the exact command or the source and destination of each copy, and which client it applies to.

A fixed command allowlist

The engine runs only claude, codex, gemini, and git, and only in argument shapes it recognizes — git is limited to init and status inside the backup folder. Anything else is refused by name.

Writes stay inside known folders

File operations are limited to the managed library, the supported client skill folders, a project root you selected yourself, and the backup area. A replaced file is moved to a rollback area rather than overwritten.

Receipts are redacted

Tokens, keys, and secret-looking values are stripped before any receipt or diagnostic bundle is written. Recorded connections store secret reference names, never values.

Honest verification words

Observed means a read-only scan found it. Installed means a write or native command has a receipt. Authenticated is never inferred; you record it after verifying in the product that owns the authorization.

Command line and Raycast

The helper ships inside the app bundle at Agent Tooling.app/Contents/Helpers/agent-tooling and shares the app's policy engine.

CommandWhat it does
scanRead-only inventory of all three clients, as JSON.
doctorSame scan plus a health verdict. Exits with status 2 when a client's command is missing.
searchQuery the local library by name, summary, bundle, or scope.
request create-skillQueue a Codex skill request for review in the app. It cannot generate or install anything itself.
planReview a plan file and print its SHA-256 digest.
applyExecute a plan, but only with the matching plan identifier and reviewed digest. Exits 3 if a step needs attention.
export-diagnosticsWrite a redacted support bundle.

Apply is deliberately hard to misuse. Editing a plan after reviewing it changes its digest, and the command then refuses to run:

agent-tooling plan changes.json                 # prints {"digest": "...", "plan": {...}}
agent-tooling apply changes.json \
  --confirm <plan-uuid> --digest <sha256>

The companion Raycast extension in integrations/raycast/agent-tooling uses that same helper, so it can search your inventory, queue a skill request, check setup, and open Sync. It cannot approve or execute anything.

Edge cases

The situations most likely to surprise you, and what the app does about each.

A client is missing

Its command reports as unavailable everywhere, and any plan step that needed it becomes a manual step explaining what to install. Configuration already on disk is still read, and skills are still written to that client's folder, so it works the moment you install the tool and run Check Setup.

One client fails, others succeed

Each client is a separate step. A failure marks the receipt as needing attention and names the failing step; the clients that succeeded keep their result. There is no all-or-nothing rollback across clients.

You edit a managed skill outside the app

Install steps carry a fingerprint of the reviewed source. If the folder changes between review and approval, the copy is refused rather than silently installing something you did not read. Run Check Setup, then review again.

A project folder moved or was deleted

Project-scoped operations re-verify the folder at approval time and refuse a path that is missing, is a symlink, or does not match the reviewed root. Re-pick the folder in the editor.

Two Macs drift apart

Nothing merges automatically. Restoring compares first: a Git backup lists conflicting skills, configurations, and sources and makes you accept them explicitly, and an encrypted restore shows what the archive contains before it replaces the managed library. The previous library is kept as a rollback artifact.

You lose the recovery key

The archive cannot be decrypted, by you or anyone else. There is no reset. Copy the key when you first enable encrypted sync, and note that importing a different key on a Mac replaces the one already in its Keychain.

A policy blocks something you want

Installing a blocked plugin is refused with a message naming the policy. Policies are data you imported, so review the source file listed in Settings → Policy & Safety.

A marketplace source is down

The reason is recorded under that source's name and the other sources keep working. One malformed listing in a catalog no longer takes down the whole catalog.

Two actions at once

Only one change may be in flight, and a prepared plan blocks other actions until you approve or discard it — otherwise the plan you are reading could stop matching reality. Adding a source or importing a repository refreshes catalogs in the background, which is why a second action right afterwards may say to wait.

The Codex generator refuses to stage a draft

It will not write into a folder other users can also write to. Keep the workspace in your home folder, where it is by default.

Something needs support

Settings → General → Export… writes a redacted diagnostics file with app, macOS, and client versions plus validation summaries. Package contents, credentials, and personal paths are excluded.

Agent Tooling runs entirely on this Mac. Credentials stay in your Keychain, your environment provider, or the client that owns them.
