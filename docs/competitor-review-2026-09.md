# Agent Tooling competitor review

Reviewed September 8, 2026. This is a product and implementation comparison, not an installation, migration, or runtime benchmark. Public source snapshots, first-party documentation and published UI screenshots were inspected alongside the current dirty Agent Tooling worktree. No competitor app was installed or executed, and no client configuration was changed.

## Recommendation

For standalone skill installation, assignment, project use and multi-device synchronization, Skills Manager is currently the stronger product. Agent Tooling should not justify its continued development by recreating that feature list or by being native SwiftUI alone.

Agent Tooling has a reason to exist if the product makes the complete Claude/Codex setup understandable: personal skills, upstream skills, intact native plugins, MCP connections, per-project placement, and reviewable changes. Those are existing foundations, but the broader configuration editor, complete Desktop coverage, hooks/agents editors, and seamless device synchronization are not finished capabilities. They cannot be counted as advantages already delivered.

The practical decision is to evaluate Skills Manager for the ordinary skill workflow before funding a large expansion of ours. Keep developing ours only for important tasks the existing products cannot handle well. If both are used, assign each managed directory a single writer; one manager can inventory the other's installations without both attempting to update or replace them.

## Skills Manager: closest substitute

Inspected version 1.38.0, commit [`10476370f6a57bdb551be328761eabbfa5d17f6c`](https://github.com/xingkongliang/skills-manager/tree/10476370f6a57bdb551be328761eabbfa5d17f6c). The website and README differ slightly in advertised agent count; the useful fact is broad support for more than 50 skill-folder adapters, not proof that it manages every feature of those agents.

### What it does better

- **A clearer primary workflow.** Library, install, agent/global workspace, project workspace and backup each have an obvious job. Published Library and Project screenshots put assignment and update actions near each skill. The same Add Skills picker keeps target agents visible and supports batch selection. This is a stronger interaction model than sending a user between inventory, configuration and sync screens for an ordinary assignment. [UI and workflows](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/README.md), [shared picker](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src/components/AddSkillsSheet.tsx).
- **Useful presets.** The same preset bar can apply a named skill selection to the current agents or project and shows partial membership. Its implementation invokes additions/removals for missing/present targets and reports partial failures. Applying a preset is a one-time action, not a promise to enforce future preset changes. Our collections and configurations can present an equally clear workflow without introducing another competing configuration type. [PresetBar](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src/components/PresetBar.tsx).
- **Substantially more developed device synchronization.** Git-backed portable metadata, skill identities, snapshots, conflict decisions, background work and recovery are implemented. The merge engine compares skill content, path and attributes separately, allowing a rename to coexist with a content edit. Competing content edits can retain the local item and queue a decision. Resolution creates a safety snapshot and offers local/remote/both. Our encrypted archive exchange does not provide this continuous merge experience. [Merge decision](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/merge/decision.rs), [resolution](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/merge/resolve.rs).
- **Broader import and source workflows.** Git repositories, local folders and archives feed a central library. Source records preserve URL, subdirectory, branch, revision and hashes; deployment records preserve client, path, mode and last synchronized source hash. Updating a Git skill stages source content, swaps the library directory, updates metadata and resynchronizes copy targets. [Source/deployment records](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/skill_store.rs), [update implementation](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/commands/skills.rs).
- **More complete agent-driven management.** A shared Rust core powers the GUI and a management CLI, with a companion skill for agents. Our CLI/MCP integration primarily reads inventory and queues human review; it does not provide the same direct mutation workflow. This is a convenience tradeoff to evaluate, not a reason to give every remote agent blanket write authority. [CLI](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/bin/skills-manager-cli.rs).

### Important boundaries

**Linked workspaces are supported.** Skills Manager can register arbitrary external skill roots, inventory enabled/disabled trees, and copy or link library content into them. These roots are excluded from global preset synchronization, while the shared workspace preset UI can apply a set once. It is not exclusively limited to the central folder. Our plan adopts central management by default with explicit advanced source/destination roles; external authorship and an external deployment destination are separate concepts. [Workspace features](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/README.md), [workspace implementation](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/commands/projects.rs).

**A source-linked installation copy is not necessarily a fork.** Skills Manager copies skill content into its library, but preserves upstream metadata and updates it. A symlink then avoids duplicate deployment bytes on supported filesystems; copy mode supports destinations where linking is unsuitable. Our own “personal copy” action means independent maintenance, a different contract. The UI should distinguish personal ownership from installation mechanics.

**Skill-folder support is not complete native-plugin support.** The inspected Claude adapter targets its skills directory; Codex adds the shared skills location for discovery. The workspace scanner explicitly skips embedded plugin/cache bundle layouts. No comparable full plugin lifecycle, MCP runtime or hooks/configuration manager was found in the inspected command and adapter surfaces. Do not extract an official bundled skill and assume its surrounding native dependencies travel with it. [Adapters](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/tool_adapters.rs), [workspace scanner](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/project_scanner.rs).

Its synchronization is substantial but deserves a real two-Mac trial. The background scheduler is driven by startup/local-change debounce and retries; remote-only edits arriving on an otherwise idle second Mac should be tested. The merge policy also uses whole-file newest-wins for presets/memberships, unlike skill-content conflicts. A pending skill touched again remotely can pause automatic merging. These source observations limit broad “everything always merges” claims; they are not runtime failure reports. [Scheduler](https://github.com/xingkongliang/skills-manager/blob/10476370f6a57bdb551be328761eabbfa5d17f6c/src-tauri/src/core/auto_backup.rs).

Published screenshots support a judgment about hierarchy and discoverability, not smoothness or speed. There is no comparable measured performance result for these competitor apps in this review.

## What Agent Tooling actually has

| --- | --- | --- |
| Native plugins | Plugin-aware discovery, bundled components, native install/update routes and availability handling | Codex updates and unsupported scopes can remain client-owned; not every vendor action is automated |

| Insights | Optional local-history analysis and aggregate recommendations | Partial observation, not a complete usage or quality measurement |

## MCP runtime specialists

**ToolHive:** the strongest integration candidate for runtime management. Its workload API already offers lifecycle, logs, upgrades and export, while Studio supplies a client-connected desktop workflow and agent playground. Our adapter can detect/list ToolHive servers today; it should grow status/log inspection first and reviewed lifecycle operations second. Do not build another container supervisor. [Workload API](https://github.com/stacklok/toolhive/blob/a1f16cefb6d7e9d70495f603df9b929beb6ba7a8/pkg/api/v1/workloads.go#L119), [Studio runtime transport](https://github.com/stacklok/toolhive-studio/blob/c31b72b9b733abc0bacd85596ab68c0b9ccf1c14/main/src/unix-socket-fetch.ts#L120).

Its tool filters both shape discovery and reject excluded direct tool calls. This would make an explicit runtime-managed subset enforceable; our existing per-tool choices are intent only. Empty filter lists in the core mean unrestricted access, so a UI cannot interpret an empty selection as “deny all.” Studio currently requires a matching registry entry for its tool-customization screen. Client groups are access to server workloads, not interchangeable with our collections: a client can subscribe to multiple groups, and deleting a runtime group can remove its servers. [Filtering middleware](https://github.com/stacklok/toolhive/blob/a1f16cefb6d7e9d70495f603df9b929beb6ba7a8/pkg/mcp/tool_filter.go#L230), [customization guide](https://docs.stacklok.com/toolhive/guides-ui/customize-tools), [group behavior](https://docs.stacklok.com/toolhive/guides-ui/group-management).

**MCPMate:** the stronger reference for per-client capability profiles and native-versus-proxy inspection. Its proxy and Inspector distinguish native and mediated access. The capability-store document combines existing storage/cache behavior with a target architecture for immutable versions, consumer bindings and publication/reconciliation; that roadmap should not be counted as fully shipped behavior. For ours, borrow a small slice: record tool-schema/description fingerprints and show what changed after a server update; offer “what this client receives” inspection. Do not transplant the whole publication infrastructure before users need it. [Capability store](https://github.com/loocor/mcpmate/blob/dc80b32f64788bf9513ccf241dd19708b25cce87/backend/crates/mcpmate-capability-store/README.md), [invocation resolution](https://github.com/loocor/mcpmate/blob/dc80b32f64788bf9513ccf241dd19708b25cce87/backend/src/core/proxy/server/tools.rs#L49), [Inspector modes](https://github.com/loocor/mcpmate/blob/dc80b32f64788bf9513ccf241dd19708b25cce87/backend/src/api/models/inspector.rs#L4).

Useful engineering references include ToolHive's locked, atomic JSON-with-comments configuration editing and MCPMate's revision-keyed bounded caches with shared in-flight work. These are patterns to adapt where our current code lacks them, not justification for another framework rewrite. MCPMate remains beta; some inspected main-branch capability work is newer than its released build. ToolHive's local container/network enforcement does not control the internals of remotely hosted servers. [Config editor](https://github.com/stacklok/toolhive/blob/a1f16cefb6d7e9d70495f603df9b929beb6ba7a8/pkg/client/config_editor.go#L29), [capability cache](https://github.com/loocor/mcpmate/blob/dc80b32f64788bf9513ccf241dd19708b25cce87/backend/crates/mcpmate-capability-store/src/cache.rs#L143), [network scope](https://docs.stacklok.com/toolhive/guides-ui/network-isolation).

## Native editing and configuration alternatives

**Chops** is the strongest native Mac editing reference in this set. Its SwiftUI split view leads directly to a list and document editor/preview. Skills, agents and rules share search, favorites and collections while retaining distinct types. Detached document/scanner loads use generation guards, and scanning deduplicates resolved physical paths. Its SSH service supports reading and writing remote libraries: useful inspiration for a Mini reached over a private network, but not a phone website. [Native layout](https://github.com/Shpigford/chops/blob/9d379d582c8b1f77491df6aabf1049e578373845/Chops/App/ContentView.swift#L12-L46), [item types](https://github.com/Shpigford/chops/blob/9d379d582c8b1f77491df6aabf1049e578373845/Chops/Models/Skill.swift#L4-L45), [SSH transport](https://github.com/Shpigford/chops/blob/9d379d582c8b1f77491df6aabf1049e578373845/Chops/Services/SSHService.swift#L15-L125).

Borrow its document actions, external-change discovery and stable selection, while keeping our requested full-width list and optional inspector. Do not copy its registry installer: that path fetches a Markdown string, writes only `SKILL.md`, and symlinks the resulting folder. Companion scripts/references/assets do not travel through that route. Plugin skills are principally read-only documents, not full managed plugin packages. The inspected README also states there is no automated test suite. None of this proves Chops is slow or unreliable at its narrower editor job. [Registry installation](https://github.com/Shpigford/chops/blob/9d379d582c8b1f77491df6aabf1049e578373845/Chops/Services/SkillRegistry.swift#L263-L305), [README](https://github.com/Shpigford/chops/blob/9d379d582c8b1f77491df6aabf1049e578373845/README.md).

**CC Switch** is the strongest ready-made alternative here if model/provider configuration becomes the main job. Its implemented skill maintenance also includes source installation, update checks, per-app deployment and restore. Its reusable app-toggle row is an especially useful response to our inconsistent selector history. Import can recover provenance from an existing agent skill lock file; ours should attempt that before asking users to paste unknown repository locations. [Shared app control](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src/components/common/AppToggleGroup.tsx#L17-L54), [skill import and provenance](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src-tauri/src/services/skill.rs#L1933-L2044), [feature documentation](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/README.md#features).

Its prompt switching preserves externally edited live instructions into the old preset/backup before writing the new selection. That is a valuable implementation contract for a future instructions editor. Its MCP form separates stdio command/args/environment from remote URL/headers while retaining generated configuration. [Prompt service](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src-tauri/src/services/prompt.rs#L117-L181), [MCP form](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src/components/mcp/McpWizardModal.tsx#L84-L151).

Important scope differences: importing an existing skill centralizes a copy and later toggles write/remove deployments; this is not our tracking-only default. Claude Desktop support explicitly excludes skill/MCP sync. The general Agents panel is a Coming Soon placeholder. WebDAV transfers database/skills snapshots and auto-uploads changes; it is not a live mobile management interface or demonstrated object-conflict merger. [Desktop support](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/docs/user-manual/en/2-providers/2.6-claude-desktop.md#support-scope), [Agents panel](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src/components/agents/AgentsPanel.tsx#L7-L18), [WebDAV implementation](https://github.com/farion1231/cc-switch/blob/f3b18df12007d0fd79fd8ad8d310880664015197/src-tauri/src/services/webdav_sync.rs#L53-L145).

## Portable skills and configuration synchronization

**Skillshare** is particularly relevant to Git-first, team and phone-access workflows. It keeps tracked repositories with Git metadata, can recreate their clones from portable configuration, and selectively projects skills into targets. Its default “merge” mode means individual symlinks that preserve unrelated local skills; it does not merge document contents. Copy mode records managed names/checksums. Whole-directory symlink mode has different ownership semantics. Tracked-repository updates reject dirty trees unless forced, but that guarantee should not be generalized to every regular install/update path. [Tracked repos](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/website/docs/understand/tracked-repositories.md), [sync modes](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/website/docs/understand/sync-modes.md), [regular source replacement](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/internal/install/install_update.go#L87-L155).

Its browser UI is real and responsive, with operational endpoints and foreground/background hosting. Default binding is loopback; remote binding/reverse-proxy deployment is documented. A Mini plus Tailscale could support phone access, but the inspected server chain does not have general application authentication. If adopting this approach, keep it behind an authenticated private access boundary rather than exposing the raw management port publicly. This is a network-access option, not hosted cross-device synchronization. [UI hosting](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/website/docs/reference/commands/ui.md), [server construction](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/internal/server/server.go#L85-L110).

Borrow its portable source/target declarations and explicit one-way transformation contracts. A transform can document fields it drops and why reverse collection is unsupported. That is a better foundation for agent-format conversion than promising equivalent behavior from arbitrary bidirectional rewriting. [Transformation contract](https://github.com/runkids/skillshare/blob/60e19f96d540e2b3fb1c28a68ef61d9fb8eb1897/website/docs/reference/commands/extras.md#L279-L348).

**Vercel Skills** is the strongest source/install protocol reference, rather than a desktop substitute. Explicit agent/scope selection, canonical installations and source locks are valuable. The project lock is sorted and timestamp-free, recording source/ref/subpath/hash without machine noise. We should support importing such provenance and consider a portable project declaration alongside our local installation baselines. A branch/tag plus a content hash is not automatically an immutable, reproducible restore. [Project lock format](https://github.com/vercel-labs/skills/blob/80feb48868972d518436f26711509bc78595b5cb/src/local-lock.ts#L5-L60), [global source metadata](https://github.com/vercel-labs/skills/blob/80feb48868972d518436f26711509bc78595b5cb/src/skill-lock.ts#L13-L37).

Its update checks batch repository/ref work; this is worth adapting for our many skills from one source. Do not replace our update review with a blind `skills update` wrapper: the inspected update dispatch reruns `add -y`, and the installer cleans destinations before copying. No equivalent local-content baseline gate was found in that path. Plugin manifests aid skill discovery but do not install a native plugin's hooks/MCP lifecycle. [Update dispatch](https://github.com/vercel-labs/skills/blob/80feb48868972d518436f26711509bc78595b5cb/src/update.ts#L690-L724), [installer](https://github.com/vercel-labs/skills/blob/80feb48868972d518436f26711509bc78595b5cb/src/installer.ts#L290-L412), [plugin discovery](https://github.com/vercel-labs/skills/blob/80feb48868972d518436f26711509bc78595b5cb/src/plugin-manifest.ts#L39-L112).

**AI Config Sync Manager** is a useful configuration-mapping reference, not an upstream skill dependency manager. It translates instructions, agent fields, permissions and terminology between clients, with dry-run, backup and receipt mechanisms. Some transformations are explicitly lossy; the inspected native-plugin path is status-only and skill symlinks are excluded. Its generated HTML board is static. Do not equate repeated reconciliation with a resident sync daemon or a phone management server. [Directional mapping](https://github.com/slash9494/ai-config-sync-manager/blob/493958615cda2ef3eda0ce4642ed96b505630fbe/rules/claude-to-codex.json), [supported boundaries](https://github.com/slash9494/ai-config-sync-manager/blob/493958615cda2ef3eda0ce4642ed96b505630fbe/README.md#L391-L415).

The best feature to borrow is its scheduled vendor-schema compatibility check and dated unsupported-field register. When a vendor adds a field, changes its description or makes a formerly unsupported feature possible, the adapter needs renewed review. This reduces drift in our native adapters without rewriting shared skill instructions or assuming that similarly named permissions mean the same thing. [Compatibility workflow](https://github.com/slash9494/ai-config-sync-manager/blob/493958615cda2ef3eda0ce4642ed96b505630fbe/.github/workflows/upstream-compat.yml), [unsupported register](https://github.com/slash9494/ai-config-sync-manager/blob/493958615cda2ef3eda0ce4642ed96b505630fbe/rules/upstream-known-unsupported.json).

## Recommended implementation sequence if we continue ours

1. **Make the everyday assignment workflow competitive.** Use one reusable Add to Apps/Project sheet with visible target chips, search, batch selection and a small outcome summary. Put presets beside that action. Reuse current configuration/binding models rather than adding another backend type. Retain the user's flat-list default; cards can be optional. Open details only when requested.
2. **Explain maintenance with actions people understand.** Personal: Edit; Upstream: Check/Review update; Native plugin: Manage in owning client; Unknown: Link source. Show package membership separately from marketplace and app placement. Keep native plugin components together. A source-linked install may contain cached/copied bytes without being an independent fork.
3. **Implement real device sync only if we retain skill ownership.** Separate portable desired state/source locks from machine paths, credentials and observed installations. Use stable IDs, per-object three-way comparison, tombstones, restore points and an explicit conflict inbox. Translate desired state into reviewed local operations on each Mac. Git is a viable transport; a hosted service is a separate product/operational commitment. Port the tested merge concepts, not raw SQLite synchronization.
4. **Extend useful integration depth.** Build the effective-settings inspector before general editors: current value, source file, scope/override, and restart requirement. Extend existing ToolHive/live-test integration for logs, runtime status and actual exposed tools. Broader agent/hook editing should follow validated client-format adapters.
5. **Make ordinary operations feel immediate.** Keep expensive scans off the UI thread, preserve cached inventory while refreshing, and show progress for the item being changed. Keep one concise review for a meaningful batch instead of making the user repeatedly navigate through the operation engine. Benchmark real inventories and test externally changed native settings; competitor screenshots are not speed evidence.

Defer a new hosted account service, an MCP runtime from scratch, a model-provider proxy, universal hook/agent translation, and more top-level navigation until the core workflow demonstrably beats the alternatives for this user's setup.

## Adoption trial that would settle the decision

Use an isolated library/project and copies of representative fixtures before giving any new manager write ownership of real agent directories. Evaluate: one personal skill with scripts/assets; one Git skill from a multi-skill repo; an upstream update after a local edit; a complete native plugin; per-agent plus project-only assignment; a preset that is partially installed; two-device rename/edit and simultaneous-content conflicts; offline reconnect; restore; and whether the phone workflow actually works. The whole-plugin case may establish a deliberate split between Skills Manager's skill library and native client/Agent Tooling ownership.

Choose **Skills Manager** if those everyday skill tasks cover the real need. Choose a **Skillshare-based workflow** if Git/CLI and a privately reachable browser UI are the priority. Keep **Agent Tooling** if complete plugin/connection/configuration visibility and reviewable changes across the existing setup are used regularly. Forking a competitor is another option, but it creates a new obligation to follow its file formats, sync protocol and upstream fixes; contributing a missing feature upstream may cost less.
